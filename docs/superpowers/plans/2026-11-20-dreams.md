# Dreams (project dreams for skills and rules) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** While the machine is idle, Shellie runs OpenCode on one chosen model over a repo's past agent sessions and
leaves proposals for the repo's checked-in skills and rules on a local branch, reviewed from Home.

**Architecture:** A new main-process area `src/main/dreams/` with pure decision modules (settings rules, readiness,
material, report, model check) around one orchestrator (`DreamRunner`) and a minute scheduler. It uses `GitClient`
directly (no Task record), spawns `opencode run` the way brain jobs do, and keeps its own record `dreams.json`.
All writes to the `dreaming` settings go through `dream:*` IPC handlers so main enforces the switch-on rules.

**Tech Stack:** Electron main (TypeScript, zod, `node:sqlite` through the existing `OpenCodeReader`), React renderer,
Vitest. No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-20-dreams-design.md` (read it first; section numbers below refer to it).

**Screens:** design canvas https://claude.ai/artifact/UpRsPykwKeKdEo2iWdQoLn (five screens). The renderer tasks
(10–12) follow it for layout and copy; where the canvas and the spec differ, the spec wins.

## Global Constraints

- Dreaming runs on OpenCode only; every run passes `-m <model>` and an inline config that pins every model and
  disables subagents. No fallback of any kind.
- `dreaming.enabled` becomes true only through `dream:switchOn`. An app update, a new repo or the generic settings
  save never changes it.
- Nothing is pushed; the main checkout and task worktrees are never touched; the agent runs no git and no shell.
- Session text stays in the user data folder and in calls to the chosen model: not in telemetry, logs or errors
  shown outside the app.
- Spawning and paths go through `Platform`; no terminal (pty tab) is opened for a dream.
- Values from the spec: idle default 10 min; scheduler tick 60 s; at most 20 tasks and 3 proposals per dream; run
  time limit 30 min; usage check every 30 s; sightings kept 90 days; back-off 1 h, then 6 h, stop after 3 failures;
  branch `dream/<YYYY-MM-DD>-<n>`; title prefix `Shellie dream`.
- Checks before every commit: `npm test`, `npm run typecheck`, `npm run lint`.
- Telemetry carries enums, counts and booleans only; new events are listed in `docs/telemetry.md`.
- The change note goes in `docs/changes/2026-11-20-dreams.md`; never edit the Status list in `CLAUDE.md`.

## Review Focus

1. The repo's own `opencode.json` or an agent file names another model: the dream must still be answered only by the
   chosen model, or be thrown away and switch dreaming off (Tasks 4, 6).
2. The machine suspends or Shellie quits mid-dream: on the next launch no dream worktree, `dream/*` branch without a
   result, or digest folder is left behind (Task 8).
3. The report is missing, not JSON, lists a file the agent did not change, or leaves a changed file unlisted: no
   crash, unlisted changes are reverted, a broken report is a failed dream (Task 5).
4. A second dream on the same day, or a `dream/<date>-1` branch left by hand: the next free `<n>` is used, never an
   existing branch (Task 6).
5. The local day changes while a dream runs under a token limit: the run is measured against the day it started in,
   and the new day starts at zero (Task 7).

```ts
  | { outcome: 'proposed'; result: DreamResult }
  | { outcome: 'nothing' }
  | { outcome: 'interrupted'; why: 'stopped' | 'limit' | 'suspend' }
  | { outcome: 'wrong-model'; answered: string[] }
  | { outcome: 'failed'; reason: string };
export class DreamRunner {
  constructor(deps: DreamRunnerDeps);
  /** Runs one dream for the repo. Never throws; cleans up on every outcome but 'proposed'. */
  dream(repo: { id: string; path: string; name: string }, o: { model: string; folders: string[]; signal: AbortSignal }): Promise<DreamOutcome>;
  running(): { repoId: string; startedAt: number } | null;
}

```

`DreamRunnerDeps` carries: `git`, `platform`, `run`, `store: DreamStore`, `dreamsDir: string`,
`sessionsOf(repoId): Promise<TaskSessions[]>`, `sessionModels(sessionId): string[]`, `now()`, and
`overLimit(): boolean` (polled every 30 s during a run; true aborts with `why: 'limit'`).

Order inside `dream` (spec §4): pick material (none → `nothing` without a worktree) → fetch (failure ignored) →
base = the repo's PR target as `resolveBase` gives it → next free `dream/<date>-<n>` → `worktreeAdd` at
`<dreamsDir>/<repoId>/<dreamId>/wt`, data in `…/<dreamId>/data` → write material → propose run → model check →
check run → model check → `readReport` → revert `outside` and `unlisted` paths → one commit per group
(`dream: <title>`) → `DreamResult`. On `proposed`: store result, add sightings, mark covered. On `nothing`: remove
worktree, branch and data, add sightings, mark covered, `succeeded`. On `failed`: remove everything, `store.failed`.
On `interrupted` and `wrong-model`: remove everything, nothing marked.
Every outcome writes one journal entry (`store.log`) with the model, the tokens the dream's sessions used and the
outcome (`interrupted` with `why: 'limit'` is logged as `limit`).

`fakeOpencode.ts` builds a small script (node, runnable through `Platform`) that plays a scripted run: reads stdin,
applies listed file edits in its cwd, writes a given `report.json`, prints OpenCode-style json events with a session
